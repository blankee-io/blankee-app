# Security

Blankee holds people's financial records on machines they run themselves. A
vulnerability here is somebody's bank balance, and an update mechanism that can
be subverted is root on their server. Reports are taken seriously and answered.

## Reporting

**Do not open a public issue.** Use either:

- GitHub's private vulnerability reporting — the **Report a vulnerability**
  button under [Security](https://github.com/blankee-io/blankee-app/security),
  which opens a private thread only maintainers can see; or
- email **info@blankee.io**.

Useful to include: the version from the footer, whether the instance is a Docker
or a Debian install, whether a bank feed is connected, and the smallest sequence
of steps that shows the problem. If you have a patch, attach it to the private
thread rather than opening a pull request — a pull request is public the moment
it exists.

You will get an acknowledgement within a few days. This is a one-maintainer
project, so a fix may take longer than that; you will be told where it stands
rather than left guessing. If you would like credit in the release notes, say so,
and how you would like to be named.

## What is in scope

- The application: authentication, session handling, the admin console,
  everything under `/api`, the widget tokens the iOS app uses.
- The update mechanism: `install/blankee_update.py`, the signature verification,
  the root helpers, and the systemd units the installer writes.
- The installer and the Docker image, including defaults that would leave a
  fresh instance exposed.
- The push relay in `relay/`.

Out of scope, and not worth your time: findings that require an attacker who
already has root on the instance, missing hardening headers with no exploitable
consequence, rate limits on a single-tenant self-hosted application, or reports
generated by a scanner with nothing behind them.

## How releases are protected

Installations update themselves, so the release path is part of the security
boundary:

- **A release is a signed tag.** `install/blankee_update.py` will only check out
  a `v*` tag whose signature verifies against the key pinned at
  `/etc/blankee/allowed_signers`. An unsigned tag, or one signed by any other
  key, is skipped and logged as skipped. Pushing to the repository is therefore
  not enough to reach an installation — the signing key is needed as well.
- **The pinned key is pinned once**, by the installer, and is never refreshed
  from the repository. If it were, whoever could push a release could swap the
  key in the same push and the signature would prove nothing. Rotating it takes
  a human on each machine, deliberately.
- **The path to the key file comes from the systemd unit**, not from any file the
  web user can write, and the updater refuses a key file that is not owned by
  root or is group- or world-writable.
- **The web process cannot choose what gets deployed.** It can only set a flag in
  a file it owns; the updater takes nothing else from it — not a branch, not a
  ref, not a remote.

If you find a way around any of that, it is the most valuable report you can
send.

## Supported versions

The newest release is the supported one. Fixes go out as a new release rather
than being backported; an instance can update in one step from any older version.
